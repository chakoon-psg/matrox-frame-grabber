## 실측값

### 추론 속도

| | 값 |
|---|---|
| 유휴 — 그쪽 2.77 ms **재현됨** | 2.696 ms (스레드 8, ORT 기본값이 8과 같다) |
| **취득 옆 · 인프로세스 · 끝에서 끝까지** | **4.9 ~ 5.7 ms** |

끝에서 끝까지는 ROI 잘라내기 + 레터박스 + 추론 + 디코드를 다 포함한다. 즉 **추론 외 전부가
약 0.3 ms**이고, 그쪽 §8의 "2% 미만"과 자릿수가 맞는다.

### 붙였을 때의 영향 — 3채널 · 120 fps · 판독 2초마다 · 3분

| | 결과 |
|---|---|
| **프레임 유실** | **0 / 0 / 0** |
| UI 응답 중앙값 | 0.10 ms → **0.10 ms** (변화 없음) |
| 처리량 사용률 | 상한(약 212회/초)의 **0.7%** |
| 판독 횟수 | 채널당 90회 |
| findings | 0건 |

### 배포 크기

| | 크기 |
|---|---|
| 라이브러리 (`onnxruntime.dll` 15.4 + 관리 DLL 0.2 + Tensors 0.4) | +16.0 MB |
| 모델 파일 (런타임 탐색, ffmpeg와 같은 취급) | +8.8 MB |
| **합계** | **+24.8 MB** |

**함정 하나.** 기본 설정이면 ONNX 패키지가 **자기가 지원하는 모든 플랫폼의 네이티브를 출력에
복사한다** — iOS 56.9 + Android 49.5 + osx-arm64 41.2 + linux 50.8 + win-arm64 15.5 MB.
처음 빌드가 **459.7 MB**로 나왔고, 그중 214 MB가 이 WPF x64 앱이 절대 못 쓰는 것이었다.
`csproj`에 `RuntimeIdentifier`를 `win-x64`로 고정해 막았다. **그 줄을 지우면 조용히 되돌아온다.**

## 구조상 가장 큰 차이 셋

cs에는 없던 제약이라, "왜 그대로 안 가져왔나"의 답이 대부분 여기 있다.

| | cs | 우리 |
|---|---|---|
| 판정자 | 모델 하나 | **타일 검출기 일곱 + 판독기.** 둘이 다르게 말할 때의 규칙은 아직 없다 |
| 취득 예산 | 없음 | **8,333 µs.** 넘으면 프레임이 조용히 사라지므로 추론은 워커에서 돈다 |
| 프레임에 그리기 | `Cv2.Rectangle` / `PutText` | **금지.** 증거가 비트 정확이라야 한다 |

**결론 하나는 이유를 고쳤다.** "3채널 매 프레임 불가"는 맞지만 예산 초과(3 × 2.77 = 8.31 ms)가
아니라 **처리량**이 이유다 — 상한 212회/초 대 필요 360회/초. 추론은 취득 예산 안에서 돌지 않고
다른 코어에서 돈다.
