## 1. UI 개선

1) **설정 창을 둘로 나눴다** — 앱 전체 설정(툴바 `Settings`)과 카메라별 설정(pane pop-out).
   경계는 **정책은 전체, 실측은 카메라별**이다. 임계값이 카메라별인 근거는 실측이다(같은 조명에서
   가장 어두운 채널만 얕은 오검출 9건, 나머지 둘은 0건).
2) **카메라 설정을 창으로 띄울 수 있게 했다** — pane이 너무 좁았다.
3) **검출 종류 체크박스를 전체 설정에 넣었다** — 일곱 종류를 전부 나열한다. 감시하지 않는
   종류도 보여야 "조용한 리그"와 "안 보고 있는 리그"가 구분된다.
4) **종류별 임계값 노브를 카메라 창에 넣었다**(Blackout → 나중에 Washout·Freeze·ColorShift·
   Flicker·Flip). 각 줄이 **그 종류의 자기 단위**로 적히고, 임계값 **옆에 지금 읽히는 값**이 붙는다.
   임계값은 옆에 측정값이 있어야 화면에서 방어된다.
5) **자동 보정 옵션을 전체 설정에 넣었다** — 라벨이
   `let a quiet run tighten Dropout on its own`이다. "자동 보정"이라고만 쓰면 일곱 종류를 다
   봐 준다고 읽힌다.
6) **타임라인을 채널·항목 단위로 바꿨다** — 평평한 밝기 선 대신 어느 장치의 어느 항목인지 보인다.
7) **되돌린 UI** — 녹화 레이트·해상도 선택(둘 다 선택지가 아니었다), RAW 녹화 버튼.
8) **실시간 갱신 버그 하나** — `BlackoutHint`가 임계값을 적용할 때만 갱신돼 멈춰 있었다.
   500 ms 틱으로 올렸다.

> 확인 방법도 바꿨다. UI Automation으로 **설정 창을 실제로 열어 내용을 읽어** 확인했다 —
> 컴파일은 XAML 요소가 깨졌는지만 말해 주고, **바인딩이 끊기면 아무 데도 기록되지 않고 빈 칸만
> 남는다.**

## 2. 이상 검지 (핵심 기능)

1) **검출기가 1종 → 7종이 됐다.**

   | 종류 | 판정하는 것 | 시점 |
   |---|---|---|
   | Dropout | 실행 기준선 대비 밝기 **하강**, 한 프레임으로 확정 | 이전부터 |
   | Blackout | **절대 레벨**이 낮고 타일이 평탄 | 09-11 |
   | Washout | 밝고 **구조가 없다**(타일 사이 spread + 타일 안 detail) | 09-13 |
   | Freeze | 프레임 간 변화가 센서 잡음 **밑으로** | 09-13 |
   | ColorShift | **밴드 비중**이 잰 기준값에서 벗어남 | 09-13 |
   | Flicker | 밝기가 **진동**(진폭 + 교차 횟수 + 대역) | 09-13 |
   | Flip | 새 프레임이 직전 프레임의 **거울상**에 더 잘 맞음 | 09-13 |

2) **공통 지속형 상태머신**(`SustainedFaultTracker`) — 일곱 중 여섯이 공유한다. dwell 양방향,
   히스테리시스, 1회 보고, 캡 없음. Dropout만 다르고 그건 취향이 아니라 `CONTEXT.md`가
   사건형과 지속형을 가르는 선이다.
3) **오검출 게이트** — coherence(타일 합의), onset spread(쓸고 지나가는 하강 기각),
   이벤트 캡(기준선이 얼어 채널이 침묵하는 것 방지), 사건당 1회 보고.
4) **임계값을 실측으로 채택했다** — 손으로 고르는 대신 실행이 제안하고 사람이 채택한다.
   1시간 정숙 실행이 처음으로 예산을 분해했고(1/시간), 2배 여유를 적용해
   Dropout 0.058 / 0.064 / 0.042, Freeze 0.0283 / 0.0225 / 0.0117을 채택했다.
5) **자동 보정 정책**(`AutoCalibrationPolicy`) — 기본 off, 그랩 종료 시 판정, 거절 사유를 로그에
   남긴다. 안전장치 셋: **조이기만 하고 풀지 않음**, **사건 0건 실행만**(되먹임 고리 차단),
   **변경폭 상한**. Dropout 하나만 건드리고, 나머지 여섯을 뺀 이유가 종류마다 다르다.
6) **밴드별 통계**(`TileGrid` + `TileReducer.WantBands`) — ColorShift만 쓴다. 옵션인 이유는
   그 루프가 취득 예산 안이라 **아무도 켜지 않은 종류는 비용을 내지 않는다**는 규칙 때문이다.

## 3. 증거 기록

1) **사건 클립** — 2초 세그먼트 링 버퍼에서 `-c copy`로 전후 N초를 잘라낸다. Rec이 아니라
   **그랩과 함께** 도는 이유는 녹화를 누르지 않은 동안 난 사건은 잘라낼 파일이 없기 때문이다.
2) **무손실 정지화면**(`StillRing`) — 사건당 4장(reference / onset / extreme / recovered).
   **클립은 x264라 편차를 재현할 수 없고 정지화면은 된다** — 둘 다 있는 이유다.
   09-13에 Freeze·ColorShift·Flip도 정지화면을 남기게 했다(Flicker는 일부러 제외 — 진동의
   한 프레임은 아무 이상 없는 그림이다).
3) **무압축 RAM 링 버퍼**(`EvidenceRing`) — 사건 구간만 Ut Video 무손실로 기록.
   용량 산출이 문서화돼 있다(±3초 · 120 fps → 카메라당 3.45 GB).
4) **덤프 직렬화**(`EvidenceGate`) — 세 채널이 동시에 660 MB를 쓰면 레이트가 57~89 fps로
   붕괴한다. 프로세스 전역 게이트로 한 번에 하나만 쓴다.
5) **사이드카에 `first_frame` / `last_frame`** — 이게 없으면 **증거 파일의 N번째 프레임이
   무엇인지 말할 수 없다.**

**검증**: 증거 파일에서 디코드한 프레임 5000이 같은 프레임의 무손실 PNG와 **바이트 단위로 동일**
(두 경로가 서로 독립인데도).

## 4. 상시 녹화

1) **5분 `.ts` 세그먼트** — 정전 내성 때문이다. 실측: 쓰던 중 죽은 MP4는 **0프레임**,
   MPEG-TS는 잘린 지점까지 전부 회수된다.
2) **인코딩 계약**(`IVideoSink` / `IHostFrameSink`) — `MIL_ID`를 받는 이유는 MIL 백엔드가
   호스트 읽기 비용을 내지 않게 하는 것이다. 두 번째 백엔드가 존재할 수 있는 구조.
3) **H.264 고정** — 세 가지로 제공했다가 실측이 닫았다(3채널 하루: 무압축 19 TB, 무손실 5.8 TB,
   H.264 1.9~3.2 GB). 게다가 MPEG-TS는 H.264만 담아 **설정 둘이 서로를 덮고 있었다.**
4) **레이트 산술을 테스트 가능한 곳으로** — `FfmpegArgs`, `VideoRatePolicy`. 녹화 결함 두 건이
   거기 살았다.
5) **저장 정책**(`StoragePolicy`) + **NAS 이동기**(`tools/move-to-nas.ps1`) — 규칙이 전부
   실측에서 나왔다(1분 이상 지난 파일만, 직렬로, 조각 단위로 간격을 두고, 해시 검증 후 삭제).
6) **MIL 싱크 슬라이스**(`tools/MilVideoSink/`) — 납품사에 넘길 독립 하네스. 도메인 로직 0.

## 5. 취득 성능

전부 **유실 프레임(`M_PROCESS_FRAME_MISSED`)으로 측정**했다. 3채널 기준이다.

| 개선 | 전 | 후 |
|---|---|---|
| 프레임 1회 추출 + 공유 풀 | 유실 60~67 / 채널 | **0** |
| 증거 덤프 직렬화 | 232 / 238 / 226, 레이트 57~89 fps로 붕괴 | 64 / 62 / 49, **120.0 유지** |
| 링 버퍼 락 경합 제거 | 64 / 62 / 49 | **6 / 4 / 4** |
| 페이지 폴트 선행 터치 | 32 / 25 / 28 | **10 / 10 / 10** (120초면 5/1/1) |

1) **프레임은 한 번만 꺼낸다** — 두 싱크가 각자 꺼내면 각 추출이 2배가 아니라 **4배** 느려졌다
   (단순 중복이 아니라 메모리 경합). 한 번으로 줄이자 **남은 한 번도 2~3배 빨라졌다.**
2) **락 안에서 memcpy하지 않는다** — `Add`가 2.37 MB 복사를 락 안에서 했고 `SlotOf`가
   1456칸 선형 탐색이었다. 복사를 락 밖으로 빼고 **회전된 순서 위의 이진 탐색**(11 비교)으로 바꿨다.
3) **운전점을 120 fps로 확정** — 124.3 fps와 비교해 덤프를 더 쓰면서 유실이 1/5이다.
   이 지점이 꼬리 지연의 무릎이다.
4) **밴드 누적 비용 실측** — reduce mean +10 / +24 / +78 µs(프레임 주기 8332 µs의 0.1~1%),
   **양쪽 다 유실 0**.

## 6. 운영·진단

1) **헤드리스 실행 스위치** — `--autostart`, `--exposure`, `--expo-scan`, `--decim`,
   `--channels`, `--no-detect` 등. 사람 없이 재고 정상 종료로 끝난다(강제 종료는 카메라
   지오메트리 노드를 잠근다).
2) **카메라 대수를 언제나 보고한다**(`cameras present: N of M`) + **카메라 0대면 `--autostart`가
   거절하고 종료 코드 2** — 빈 포트와 남의 손에 있는 보드가 `MdigAlloc`에서 똑같이 던지고
   똑같이 조용했다. 이걸 몰라서 **밤샘 16시간을 잃었다.**
3) **캠페인 스크립트**(`scripts/run-campaign.sh`) — 시작 전 다른 인스턴스 확인, 매 시간
   종료 요약이 남았는지 **타임스탬프로** 확인(건수로 세면 로그 회전에 오탐한다).
4) **프로세스별 로그 + MIL 오류 로그** — 한 로그 파일을 여러 인스턴스가 쓰므로 pid를 찍는다.
5) **자율 실행 재개 경로**(`docs/agents/autonomous-run.md`) — 컨텍스트가 끊겨도 그 파일만
   읽으면 이어갈 수 있다.

## 이번 주에 배운 것 (다음 주에 쓸 것)

1) **실행 길이보다 리그 상태가 바닥을 더 크게 정한다.** Dropout 바닥이 0.0087 → 0.0580으로
   6.7배 올랐는데 **두 실행 모두 한 시간**이었다. 달라진 건 화면이 움직였다는 것뿐이다.
   → **조용한 한 시간을 더 사지 말고 다른 조건을 살 것.**
2) **바닥의 방향이 종류마다 반대다.** Dropout·Flicker·Washout은 최대값형(길수록 올라감),
   Blackout·Freeze·Flip은 최소값형(길수록 내려감). 모르면 실행 길이를 잘못 고른다.
3) **잰 바닥이 항상 임계값의 근거는 아니다.** 바닥이 **지배적인 오검출 원인**을 담고 있을 때만
   그렇다. ColorShift는 아니다(바닥은 센서 잡음, 실제 원인은 화면 색).
4) **측정 중에는 그 PC에서 아무것도 돌리지 말 것.** 빌드 하나가 유실 3~11프레임을 만든다.
