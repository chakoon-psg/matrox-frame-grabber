# 판독기를 ROI 로케이터로 — 상시 동작 설계 (2026-09-16)

세 번 고쳐 쓴 문서다. 처음 요청은 "판독기에 잘라낸 ROI 대신 전체 화면을 넘기자"였고,
설명을 거쳐 **무엇을 위한 장치인지**가 확정됐다:

> **주변 환경이 바뀌어 장비가 옮겨졌을 때 검출 ROI를 유동적으로 다시 잡는 장치.**
> 고속 추적이 아니므로 **디스플레이 버퍼**에서 읽으면 된다.
> **그렇게 정해진 ROI를 기준으로 고속 검출(타일 7종)이 돈다.**
> **상시로 도는 기능이다.**

이 문서는 ① 그 역할이 지금 적용돼 있는지, ② 디스플레이 버퍼 경로가 성립하는지,
③ **상시로 돌 때** 무엇이 필요한지를 코드로 확인한 결과다. 추정에는 **[추정]**을 붙였다.

관련: [`adr/0002`](adr/0002-screen-inspector-as-a-removable-slice.md) ·
[`cs-adoption-summary.md`](cs-adoption-summary.md) ·
[`measurements/2026-09-14-inspector-before-after.md`](measurements/2026-09-14-inspector-before-after.md)

## 0. 결론

**그 역할로는 적용되지 않았다.** 원본 cs는 전체 화면을 받아 **대상 박스**를 내놓는 로케이터인데,
우리 앱에는 **ROI 크롭을 받아 이상 종류를 말하는 판독기**로 바뀌어 붙었다. 지금 배선은 순환이다 —
사람이 그린 ROI를 넣고 모델에게 그 안에서 찾으라고 한다.

**디스플레이 버퍼 경로는 성립하고, 상시로 돌려도 남는다.** 2026-09-16에 쟀다 —
**취득 옆에서 초당 118회**(전체 프레임, decim 2, median 8.46 ms)이고, 라운드로빈 상시 운전이
쓰는 것은 그 **1.7%**다. 그리고 **고속 검출은 184.1 fps 그대로였다** — 대조군이 오히려 더 많이
잃었다. 취득 훅도 프레임 풀도 지나지 않는다.
→ [`measurements/2026-09-16-locator-throughput.md`](measurements/2026-09-16-locator-throughput.md)

**상시 추적에서 위험한 것은 비용이 아니라 되먹임이다** — ROI가 고장을 피해 움직이면 일곱 검출기가
조용해진다. 그것을 막는 것은 사람의 수락이 아니라 **인터록 다섯 개**이고, 전부 이 저장소에 이미
있는 재료로 만들어진다(§5).

## 1. 역할 확인 — 지금은 반대로 붙어 있다

**원본 cs** (`C:\projects\cs\Program.cs`): 웹캠 **전체 프레임**을 `Predict`에 넣고 박스 좌표를
엑셀에 시계열로 쌓는다. 산출물이 좌표 그 자체다 — *"무엇이 잘못됐나"*가 아니라 *"그것이 어디 있나"*.

**우리 앱** (`CameraChannel.cs:2336`):

```csharp
byte[] bgr = _letterbox.Fill(frame, frameWidth, frameHeight, rx, ry);  // rx,ry = _analysisRoi
int n = inspector.Inspect(bgr, _findings);
for (...) MilErrorLog.Note($"... {f.Kind} (\"{f.Label}\") ... in the region");
```

`_analysisRoi`를 설정하는 경로는 네 개이고 **전부 사람이다** — 설정 창 입력 상자,
마우스 드래그(`RoiEditSurface`), 전체 프레임 복귀, settings.json 로드.
**모델이 거기에 닿는 줄은 없다.**

숨겨진 것은 아니다. ADR 0002가 어휘를 `Kind`/`Label`(이상 종류)로 정하면서 이미 판정 쪽으로 갔고,
09-14 실측 문서 ⑥은 이 차이를 *"설계는 전체 프레임, 실제는 분석 ROI → 축소가 아니라 확대"*라는
**기하 문제로만** 적었다. 맞는 관찰이지만 **입력이 바뀌면 역할이 바뀐다**는 데까지 가지 않았다.

**그리고 이 배선에서는 목적을 이룰 수가 없다.** 장비가 옮겨져 ROI가 어긋나면 모델은
**어긋난 ROI 안만** 보므로 어긋났다는 사실을 알 방법이 없다.

## 2. 앞선 검토의 "12.9배 손실"은 이 역할에 해당하지 않는다

| | 판정 역할 (현재 배선) | **로케이터 역할 (이번 목적)** |
|---|---|---|
| 찾는 대상 | ROI 안의 결함 (글자 깨짐, 아이콘 누락) | **패널 자체** |
| 전체 프레임을 넣으면 | 대상이 12.9배 작아짐 → 치명적 | 대상이 모델 안에서 **약 89×55 px** — 큰 객체다 |
| 격자 (stride 4, **모델 메타데이터로 확인** — `grid 80x64`) | 결함이 한 칸 아래로 떨어짐 | **22×14 칸** — 충분하다 |
| decimation | ROI 크기가 따라 변함 | **무관** — 전체를 레터박스하므로 비율이 항상 같다 |

**로케이터에게 전체 프레임은 손실이 아니라 전제다.**

조건 하나. cs 문서 §0-4 — **int8 `wh` head가 약 62 px에서 포화한다.** 패널 폭이 모델 안에서
약 89 px이므로 **int8이면 박스가 잘린다.** 지금은 fp32라 문제없지만, 속도를 이유로 바꾸면
로케이터가 조용히 망가진다(fp32가 같은 머신에서 2.2배 빠르기도 하다).

## 3. 디스플레이 버퍼 경로 — 성립한다

### 3.1 코드로 확인한 것 넷

| | 확인 | 근거 |
|---|---|---|
| ① | **크기·밴드가 취득 프레임과 같다** | `MbufAllocColor(sizeBand, sizeX, sizeY, …)`를 `MdigInquire`의 현재 페이로드로 할당 (`CameraChannel.cs:1614`) |
| ② | **좌표계가 `_analysisRoi`와 같다** | 코드 주석이 명시 — *"both are in pixels of the acquired, already-decimated frame"*. 변환이 필요 없다 |
| ③ | **페이지드 메모리이고 읽을 수 있다** | `M_IMAGE + M_DISP + M_PROC` — `M_GRAB`이 **일부러 빠져 있다**. grab 링 버퍼의 비페이지드/DMA 풀과 다른 메모리다 |
| ④ | **같은 자리에서 같은 일을 하는 선례가 있다** | `BrightnessMeter.Sample(_dispBufId, _analysisRoi)`가 500 ms 틱에서 `MbufChildColor` + strip 읽기로 돈다 |

### 3.2 상시로 돌려도 남는다 — 숫자

| | 타일 검출기 (고속) | 판독기 — 현재 배선 | **로케이터 — 상시** |
|---|---|---|---|
| 도는 자리 | 취득 훅 (예산 8,333 µs) | 워커 + `SharedFramePool` hold | **500 ms 틱 + 워커** |
| 메모리 | grab 링 (비페이지드/DMA) | 공유 프레임 풀 (채널당 47 MB) | **디스플레이 버퍼 (이미 있음)** |
| 취득 DMA 경합 | 있다 | 있다 (hold 동안) | **없다** |
| 프레임 유실 위험 | 직접적 | 간접적 | **없다** |
| 추가 메모리 | — | — | **0** |

처리 속도는 2026-09-16에 쟀다 — **취득 옆(3채널 · 184.1 fps · 일곱 종류)에서 한 번에
8.46 ms(median), 초당 118회.** 유휴에서는 3.44 ms · 291회/초다.

| 상시 주기 | 3채널 합 | 1초에 쓰는 시간 | **duty** |
|---|---|---|---|
| 매 틱, 세 채널 모두 (채널당 0.5초) | 6.0회/초 | 50.8 ms | **5.1%** |
| **틱마다 한 채널씩 (라운드로빈, 채널당 1.5초)** | 2.0회/초 | 16.9 ms | **1.7%** |
| 2초에 1회 (현재 판독기와 같은 주기) | 1.5회/초 | 12.7 ms | 1.3% |

**그리고 초당 118회를 쉼 없이 돌리는 최악 부하에서도 취득이 깎이지 않았다** — 벤치를 돌린
180초가 유실 145/365/144, 대조군이 254/458/237이다(원인은 리그의 사건 활동과 184 fps이지
로케이터가 아니다).

**상시가 비용 문제를 만들지 않는다.** 라운드로빈을 권하는 이유는 용량이 아니라 UI 스레드다(§4.2).

### 3.3 덤 — 학습 데이터가 같은 버퍼에서 나온다

`StillRing`도 스냅샷도 **디스플레이 버퍼**에서 나온다(`ring.Allocate(_sysId, _dispBufId, …)`,
`MbufExport(path, M_PNG, _dispBufId)`). **라벨링할 PNG와 로케이터가 볼 픽셀이 같은 경로**다.

## 4. 경로에 걸리는 함정 넷

### 4.1 정지 상태의 디스플레이 버퍼는 **이전 실행의 마지막 프레임**이다

`CLAUDE.md`에 실측으로 적혀 있고 `Snap` 버튼이 `IsGrabbing`에 묶인 이유다.
목적이 *"장비를 옮긴 뒤"*이므로 **옮기고 그랩 전에 돌면 옮기기 전 장면에서 ROI를 제안한다.**
그리고 그 제안은 그럴듯해 보인다.

- **`IsGrabbing` 게이트 필수.** 메서드 안에서도 거부할 것.
- 프리뷰 스로틀(`DisplayUpdateFps`)이 낮거나 0이면 버퍼가 오래된 프레임일 수 있다.
  **마지막 복사 시각(`_lastDispCopyMs`)을 함께 보고 오래됐으면 한 틱 미룬다.**

### 4.2 틱은 UI 스레드다 — MIL 읽기만 틱에서

실측 UI 지연은 중앙값 0.10 ms, p99 7~8 ms. 여기에 **판독 1회 8.46 ms**(취득 옆 median,
p90 10.0, max 12.9 — 2026-09-16 실측)를 얹으면 사람이 알아채는 멈칫이다.

```
틱 (UI 스레드) : 밴드 셋 MbufGet2d → 2.37 MB      [추정] 0.5~1 ms   ← 한 채널만 (라운드로빈)
워커           : 레터박스 1.5 ms + 추론·디코드 6.9 ms = 8.46 ms   (실측, 취득 옆)
```

MIL 읽기를 틱에 두는 이유는 **디스플레이 버퍼를 만지는 다른 코드가 전부 이 스레드에 있기
때문**이다(`BrightnessMeter`, 스냅샷, `StillRing`). 워커에서 동시에 만지는 조합은 확인된 바 없다.
한 번에 하나만 돌게 하는 인터록(`_inspectBusy`)은 이미 있다.

### 4.3 밴드 순서 — 여기서 틀리면 **조용히** 못 찾는다

`BgrLetterbox`는 평면 순서가 **gbrp**라고 가정한다(`offG = 0, offB = plane, offR = plane*2`).
`MbufChildColor`의 이 저장소 관례는 **0 = R, 1 = G, 2 = B**다.
**인덱스를 그대로 넘기면 채널이 뒤바뀌고**, 색 기반 클래스에서는 예외도 오류도 없이
**아무것도 못 찾는** 형태로만 드러난다 — 지금 findings 0건과 구별되지 않는다.

### 4.4 박스를 그대로 ROI로 쓸지는 정책이다

`BrightnessMeter`의 주석이 근거를 이미 적어 뒀다 — *"패널 주변 배경이 dropout을 희석한다.
패널이 프레임의 절반을 채우면 그래프에 닿는 하강이 절반이 된다."*
**박스를 그대로 쓰면 가장자리의 베젤·반사가 섞인다.** 안쪽으로 몇 %를 줄일지는 정하고
로그에 남길 것. `ChannelRoi.Snap`이 짝수 격자(Bayer CFA phase)로 한 번 더 줄인다.

## 5. 상시 추적 설계 — 인터록 다섯, 전부 있는 재료로

상시 동작에서 비용은 문제가 아니다(§3.2). 문제는 **되먹임**이다:
패널이 어두워지면 로케이터가 그것을 "패널이 아니다"로 읽고, ROI가 **고장을 피해 움직이고**,
일곱 검출기가 엉뚱한 픽셀을 보며 조용해진다. 아무 지표도 흔들리지 않고 `DetectionOff`도 아니다.

**그래서 상시 추적의 본체는 추적기가 아니라 이 다섯이다.**

| | 인터록 | 무엇을 막나 | 있는 재료 |
|---|---|---|---|
| **T1** | **못 찾으면 안 움직인다 (hold)** | findings 0건 또는 점수 미달이면 직전 ROI 유지. **꺼진 패널은 못 찾히므로 ROI가 도망갈 수 없다** — 되먹임의 대부분이 여기서 끊긴다 | `ScoreThreshold`가 이미 옵션에 있다 |
| **T2** | **사건 중에는 얼린다 (freeze)** | 일곱 중 하나라도 진행 중이면 ROI 고정. **검출기가 볼 것을 치워 주지 않는다** | `SustainedFaultTracker.InFault`가 종류마다 있고 채널이 일곱을 전부 필드로 들고 있다 — OR 하나 |
| **T3** | **dwell — 연속 N회 같은 제안일 때만 움직인다** | 한 번의 잘못된 박스로 움직이지 않는다 | 저장소 관례 그대로: **ms로 설정하고 틱 수로 센다** |
| **T4** | **데드밴드 — IoU가 임계 이상이면 무시** | 매 틱 1~2 px 흔들림. 없으면 `Snap`의 짝수 격자 경계에서 **계속 왕복한다** | `CenterNetDecoder`에 IoU가 이미 있다 |
| **T5** | **이동·크기 변화 상한** | 텔레포트 금지. 한 번에 옮길 수 있는 거리와 크기 비율을 제한 | 자동 보정의 "변경폭 상한 2배"와 같은 계열 |

**그리고 이동은 기록한다.** 이전/이후 사각형, 점수, 프레임 번호. 증거 사이드카의 감사 한 줄과
같은 성격이다 — 나중에 *"그 판정은 어느 영역에서 나온 것인가"*에 답해야 한다.
**ROI가 움직인 실행과 고정이었던 실행은 다른 실행이다.**

**사람이 그리면 그것이 기준이 된다.** 드래그·입력이 들어오면 추적기를 리셋하고 그 사각형을
새 기준으로 삼는다. 사람의 손이 모델에게 덮이면 안 된다.

### 5.1 위치와 크기를 같은 눈으로 보지 않는다

| | 타일 기하 | 임계값 근거 | 상시 추적에서 |
|---|---|---|---|
| **위치 이동** | 8×8 격자 모양이 그대로 | 거의 보존 (같은 패널, 같은 픽셀 수) | **자유롭게 따라간다** |
| **크기 변화** | 타일당 픽셀 수가 바뀐다 | **바닥이 움직인다** — 타일 평균의 잡음이 픽셀 수에 따라 달라진다 | **허용 오차 안에서만.** 밖이면 임계값을 stale로 표시 |

장비가 옮겨지면 거리도 바뀔 수 있으니 크기 변화를 막을 수는 없다. 대신
**허용 오차(예: ±5%)를 넘는 크기 변화는 "이 영역에서 잰 임계값이 아니다"로 표시**한다.

### 5.2 그래서 `CalibrationRoi`가 먼저다

임계값은 카메라별 실측이고 **그 ROI 안의 픽셀**에서 나왔다. 그런데 캘리브레이션이 남기는 것은
셋뿐이다:

```csharp
public string CalibratedAt { get; set; }      // 언제
public long   CalibrationFrames { get; set; } // 몇 프레임
public double CalibrationFloor { get; set; }  // 바닥이 얼마
```

**어느 영역에서 쟀는지가 없다.** 사람이 드래그하는 지금도 구멍이지만, **상시 추적이 켜지면
매번** 그렇게 된다. 로케이터를 붙이기 전에 저장할 것.

## 6. 층 구조 — 아래층은 바꿀 것이 없다

```
디스플레이 버퍼(전체 화면) ──→ 로케이터(판독기) ──→ 인터록 5 ──→ _analysisRoi
   500 ms 틱, 페이지드            상시, 라운드로빈      T1~T5          │
                                                                     ▼
                                                        타일 검출기 일곱 (고속, 취득 훅)
```

타일 일곱은 이미 `_analysisRoi`를 기준으로 돈다. 바뀌는 것은 **ROI의 출처** 하나뿐이다.

## 7. 장단점

| 관점 | Pros | Cons |
|---|---|---|
| 목적 | **장비가 옮겨져도 검출 영역이 따라간다** — 지금은 사람이 드래그로만 한다 | 되먹임 위험. 인터록 다섯이 본체다(§5) |
| 역할 | 순환이 풀린다. 모델이 답을 받는 대신 답을 낸다 | 이상 판정 역할은 당분간 보류 — 타일 일곱이 계속 그 일을 한다 |
| 경로 | 취득 훅·프레임 풀·hold 계수를 안 지난다. **추가 메모리 0** | 디스플레이 버퍼의 정지 함정(§4.1) |
| 성능 | **초당 118회**(취득 옆 실측). 라운드로빈 상시가 그 **1.7%**. 취득 레이트 영향 없음(대조군 확인) | 틱과 워커를 안 나누면 UI 멈칫 **8.46 ms**(§4.2). decim 1이면 11.8 ms로 는다 |
| 정확도 | 대상이 모델 안에서 89×55 — 충분히 크다 | **int8이면 62 px에서 박스 절단** |
| 구조 | 계약(`Inspect(bgr) → ScreenFinding[]`)을 **안 바꿔도 된다**. 소비자만 바뀐다 | 추적기·인터록·`ChannelRoi` 변환이 새로 필요 |
| 데이터 | 라벨은 사각형 하나, 아무 프레임이나. PNG가 같은 버퍼에서 나온다 | 패널을 배운 모델이 아직 없다 |
| 운영 | 실행 중 ROI 이동이 로그에 남는다 | `CalibrationRoi` 없이는 임계값 근거가 조용히 무효가 된다(§5.2) |

## 8. 권고

**A. 역할을 ADR 0002에 적는다.** 지금 문서에 로케이터가 없다. 판독기가 답하는 질문이
*"무엇이 잘못됐나"*인지 *"그것이 어디 있나"*인지를 적지 않으면 다음 사람도 같은 자리에서 갈린다.
**둘 다 필요하면 둘 다 적는다** — 층이 다르므로 공존한다(§6).

**B. 디스플레이 버퍼 + 틱 경로, 라운드로빈으로 상시.** 채널당 1.5초 간격이면 duty 1.7%이고
UI 스레드 부담이 매 틱 한 채널분이다. 틱에서는 MIL 읽기만, 레터박스·추론은 워커로.

**C. 인터록 다섯을 추적기와 같이 만든다(§5).** 특히 **T1(못 찾으면 유지)과 T2(사건 중 동결)** —
이 둘이 "ROI가 고장을 피해 움직인다"를 직접 막는다. 둘 다 있는 재료로 만들어진다.

**D. `IsGrabbing` 게이트를 먼저 건다.** 정지 상태의 버퍼는 이전 실행의 마지막 프레임이고,
이 기능의 목적상 그 실패가 가장 그럴듯한 얼굴로 나타난다(§4.1).

**E. `CalibrationRoi`를 저장한다.** 상시 추적이 켜지면 임계값의 근거가 매번 바뀐다(§5.2).
크기 변화가 허용 오차를 넘으면 임계값을 stale로 표시한다.

**F. ROI 이동을 기록한다.** ROI가 움직인 실행과 고정이었던 실행은 다른 실행이다.

**G. 밴드 순서를 gbrp로 맞춘다.** 틀리면 오류 없이 "아무것도 못 찾음"으로만 나타나고,
지금 상태와 구별되지 않는다(§4.3).

**H. int8로 바꾸지 않는다.** `wh` head 포화가 곧 박스 절단이다(§2).

**I. 모델은 로케이터용을 먼저 만든다.** 클래스 하나(패널), 큰 객체, 프레임당 사각형 하나,
사건이 아니라 아무 프레임이나 쓴다 — 이상 판정 모델보다 도달 가능한 목표다.

## 9. 이 보고서가 말하지 않는 것

- **로케이터 정확도를 잰 값이 없다.** 89×55가 "충분히 크다"는 것은 기하와 cs 문서의 포화 한계에서
  나온 판단이지, 우리 패널로 확인한 검출률이 아니다.
- **인터록의 값(dwell 횟수, IoU 데드밴드, 이동 상한, 크기 허용 오차)은 전부 미정이다.**
  이 저장소의 규율대로 **실측으로 정할 값**이고, 그러려면 패널을 배운 모델이 먼저 있어야 한다.
- **디스플레이 버퍼를 워커에서 직접 읽어도 되는지는 확인된 바 없다.** 그래서 §4.2는 읽기를
  틱에 두는 쪽을 권한다.
- **처리 속도는 별도 프로세스에서 쟀다.** 로케이터가 아직 앱에 없기 때문이다. 09-14 실측에서
  인프로세스가 약 0.3 ms 컸으므로 같은 폭이면 8.46 → 약 8.8 ms다.
- **틱 쪽 읽기 비용 [추정] 0.5~1 ms는 재지 않았다.** `BrightnessMeter`는 strip만 읽으므로
  전체 프레임 읽기의 실측이 이 저장소에 없다.
- **타일 검출기를 전체 프레임으로 바꾸는 것은 여전히 안 된다** — 취득 훅 안이라 reduce가
  **[추정]** 204 µs → 3.2 ms가 되고 호스트 읽기가 채널당 284 MB/s 는다.
