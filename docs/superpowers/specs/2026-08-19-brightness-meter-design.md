# 카메라별 밝기 실시간 미터

작성일: 2026-08-19

## 배경

운영 중에 각 카메라의 노출이 건강한지 — 너무 밝거나 어둡지 않은지, 하이라이트가 물리고 있지
않은지 — 볼 방법이 없다. 문제는 녹화된 영상을 나중에 열어 봐야 드러난다. 포화된 화소는
후처리로 복구할 수 없으므로, 그때 발견하는 것은 이미 늦다.

세 카메라가 같은 조명을 같게 보고 있는지도 지금은 눈대중으로만 판단한다.

## 목표

카메라별 밝기를 수치화해 창 하단의 공통 시간축 그래프에 실시간으로 표시한다.

**가장 강한 제약은 성능이다.** 취득 경로에 어떤 영향도 주지 않는다.

## 설계

### 1. 성능 불변식

**`CameraChannel.OnGrabbedFrame`에 코드를 추가하지 않는다.** 이것은 취향이 아니라 검증 가능한
인수 기준이다 — 최종 diff에서 그 메서드가 손대지 않았음을 확인한다.

CLAUDE.md가 경고하듯 훅에 추가하는 작업은 취득 예산 안에서 돈다. 2064×1544 3밴드를
184fps × 3채널로 훑으면 프리뷰가 느려지는 정도가 아니라 grab이 정체되고, RAW 경로에서는 즉시
`M_PROCESS_FRAME_MISSED`로 나타난다.

측정은 전부 기존 **500ms `DispatcherTimer`** 위에서 돈다. 취득 스레드와 공유하는 것은
디스플레이 버퍼를 읽는 행위 하나뿐이다.

**선례:** `SaveSnapshotToOutput()`이 이미 그랩 중에 UI 스레드에서 `_dispBufId`를 읽는다
(`MimResize` + `MbufExport`, `CameraChannel.cs:855-861`). 검증된 패턴이다. 읽는 중에 훅이 새
프레임을 덮어써도 무해하다 — 두 프레임이 섞인 값이 나올 뿐이고 그것도 실제 화소 데이터다.

### 2. 측정 지표 — Rec.601 luma + 포화율

```
Y = 0.299·R + 0.587·G + 0.114·B
```

**Rec.709가 아니라 Rec.601을 쓴다.** 이 프로젝트에만 있는 이유가 있다. Bayer 모자이크의 단순
평균은 CFA가 1R:2G:1B라 실질 가중치가 `0.25 / 0.50 / 0.25`인데:

| | R | G | B | Bayer 평균과의 거리 합 |
|---|---|---|---|---|
| Bayer 단순 평균 | 0.25 | 0.50 | 0.25 | — |
| **Rec.601** | 0.299 | 0.587 | 0.114 | **0.272** |
| Rec.709 | 0.2126 | 0.7152 | 0.0722 | 0.430 |

RAW 녹화를 시작하면 버퍼가 Bayer 모자이크로 바뀐다. 709를 쓰면 그 순간 그래프가 계단처럼
튀고, 601을 쓰면 거의 이어진다.

**평균만으로는 부족하다.** 평균 luma는 화면이 망가져도 미동하지 않을 수 있다 — 프레임 절반이
255로 날아가고 나머지가 어두워지면 평균은 그대로다. 노출이 서서히 올라가 하이라이트가 물리기
시작해도 평균은 완만히 오를 뿐이다.

그래서 한 번의 화소 순회에서 세 값을 함께 낸다:

- **평균 luma** (0-255)
- **포화율** — 값이 255인 화소의 비율
- **흑화율** — 값이 0인 화소의 비율

**감마는 건드리지 않는다.** 표준 luma 공식은 감마 인코딩된 값에 그대로 적용하는 것이 정의이고,
노출 감시 목적에는 그것이 맞다. 포화와 센서 saturation이 인코딩된 영역에서 일어나기 때문이다.
선형화는 물리적 조도 변화를 재려는 경우에만 의미가 있으며, 이번 범위 밖이다.

### 3. 표본 추출 — 축소가 아니라 점 추출

**`MimResize`로 줄여서 재면 안 된다.** 바이리니어 축소는 평균에는 좋지만 **포화 화소를 뭉개서
없앤다.** 255 옆에 200이 있으면 227이 되어 포화로 세어지지 않는다. 정작 잡으려던 실패를 못 잡게
된다.

원본 해상도의 **디스플레이 버퍼**에서 점을 뽑는다. 높이 방향으로 균등하게 퍼진
**16개 스트립(각 4행, 합계 64행 × 2064열)**을 `MbufGet2d`로 읽는다.

| | 전수 스캔 | 스트립 샘플링 |
|---|---|---|
| 화소/채널/틱 | 3,186,816 × 3밴드 | 132,096 × 3밴드 |
| 3채널 2Hz 총량 | 약 55 MB/s | 약 2.4 MB/s |

13만 화소면 비율 추정 오차가 ±0.3%p 수준이라 포화율 판정에 충분하다. 스트립을 세로로 흩뿌리는
이유는 화면 위쪽 광원 같은 공간 편향을 놓치지 않기 위해서다.

밴드 읽기는 CLAUDE.md의 규칙을 따른다:

- `MbufGetColor`를 쓰지 않는다 — 패킹 경로는 이 버퍼들에서 멈추고 플래나 경로는 0을 돌려준다.
- `MbufChildColor`로 밴드 자식을 만들어 두고 각각 `MbufGet2d`로 읽는다.
- `MbufGet`이 아니라 `MbufGet2d`다 — pitch 패딩(2112 > 2064) 때문이다.
- 자식은 부모보다 **먼저** 해제한다.

### 4. 미해결 — `MimStat` 가용성

`MimStat`이 이 장비에서 동작하면 전수 통계를 MIL이 처리하므로 표본 추출 자체가 불필요해진다.
라이선스 조회는 `M_LICENSE_LITE`만 보고했지만 **실제로 `MimResize`와 `MimShift`가 프로덕션에서
동작 중**이므로(`RecordingSession.cs:148,152`) 단정할 수 없다.

구현 계획의 첫 작업에서 확인한다. 결과에 관계없이 설계는 성립한다 — 두 경로가 같은 인터페이스를
채우고, 폴백인 스트립 샘플링이 이미 충분히 싸다.

### 5. 구성요소 — 새 파일 두 개

`CameraChannel`은 이미 1471줄이고 모델이자 뷰모델이다. 여기에 더 얹지 않는다.

- **`src/Mil/BrightnessMeter.cs`** — 한 채널의 MIL 버퍼에서 표본을 읽어 세 값을 계산한다.
  밴드 자식의 수명을 소유한다.
- **`src/Infrastructure/BrightnessHistory.cs`** — 고정 크기 링 버퍼. 240 샘플 = 2Hz × 120초.
  **MIL 호출 0회**로, `src/Infrastructure/` 전체가 지키는 성질(하드웨어 없이 테스트 가능)을
  유지한다.

메모리는 샘플 12바이트 × 240 × 4채널 = 약 12KB.

### 6. UI — 창 하단의 접히는 스트립

전 채널을 **하나의 공통 시간축**에 겹쳐 그린다. 카메라 간 차이가 즉시 보이는 것이 이 배치의
목적이며, 채널별로 그래프를 나누면 그 비교가 사라진다.

```
┌──────────────────────────────────────────┐
│  [toolbar]                    [▼ 밝기]   │
├────────────────────┬─────────────────────┤
│      CAM 0         │       CAM 1         │
├────────────────────┼─────────────────────┤
│      CAM 2         │    (No camera)      │
├────────────────────┴─────────────────────┤
│ 밝기  ─cam0 ─cam1 ─cam2      포화 0.2%   │
│ 200┤      ╭─╮                            │
│ 100┤ ─────╯ ╰────────────────            │
│   0└──────────────────────── -120s → now │
└──────────────────────────────────────────┘
```

- **세로축은 0-255 고정.** 자동 스케일은 드리프트를 숨겨서, 정작 보려던 변화를 안 보이게 만든다.
- **포화율은 선을 추가하지 않고 숫자로 표기한다.** 축이 다른 두 계열(0-255과 0-100%)을 한
  그래프에 겹치면 오독을 부른다. 채널별 현재값을 범례 옆에 쓴다.
- **포화율이 1%를 넘으면 그 채널의 숫자를 경고색으로 표시한다.** 1%는 임의의 출발점이며,
  현장에서 조정할 수 있도록 상수 하나로 둔다. 자동 조정이나 알람은 하지 않는다 — 범위 밖이다.
- 렌더링은 채널당 `Polyline` 하나에 `PointCollection`을 타이머에서 갱신하는 방식이다.
  240점 × 4채널은 WPF가 여유롭게 처리한다. **차트 라이브러리는 추가하지 않는다.**
- 채널 선 색은 `Styles.xaml`에 4색을 새로 정의한다. 다크 배경에서 서로 구분되고, 기존
  강조색(녹화 상태 표시 등)과 혼동되지 않아야 한다.
- **토글은 툴바 오른쪽 끝에 버튼 하나**로 둔다. 접으면 비용이 0이고, 펼치면 2×2 격자에서
  세로 100px 정도를 가져간다.
- **카메라가 없거나 grab 중이 아닌 채널은 선을 그리지 않고 범례에도 넣지 않는다.** 표본을
  수집하지도 않는다 — 디스플레이 버퍼에 유효한 화면이 없기 때문이다.

이 배치를 고른 이유는 대안 둘의 결함 때문이다.

- **4번 패널에 그래프 3개**: 4번 채널이 계속 빈다는 가정에 의존한다. 이 앱은 최대 4대를
  전제로 만들어졌고 보드는 카메라가 3대여도 항상 디지타이저 4개를 보고한다. 4번째 카메라를
  꽂으면 그래프가 갈 곳을 잃는다. 2×2 격자의 한 칸은 시계열 3개를 쌓기에 나쁜 모양이기도 하다.
- **카메라별 별도 창**: 라이브 화면 셋을 보면서 창을 따로 띄우면 비교가 안 된다. 이 앱은 이미
  전체화면 오버레이에서 MIL이 키보드 메시지를 가로채는 문제로 고생한 전력이 있다
  (`ComponentDispatcher.ThreadFilterMessage`). 창을 더 늘리면 그 종류의 비용을 다시 낸다.

### 7. RAW 녹화 중 처리

RAW 녹화는 `M_BAYER_CONVERSION`을 끄고 디스플레이 버퍼를 band-1로 바꾼다.

`M_SIZE_BAND`를 조회해 1이면 그 값을 그대로 luma로 쓴다. Bayer 모자이크 평균이 Rec.601과 거의
같으므로 그래프가 이어진다(2절 참고).

## 검증 방법

이 리포에는 테스트 프로젝트가 없다. 확인 절차를 명시한다.

1. `git diff`에서 `OnGrabbedFrame`이 **한 줄도 바뀌지 않았음**을 확인한다.
2. **3채널 grab + RAW 녹화 중 `M_PROCESS_FRAME_MISSED`가 증가하지 않는지** — 미터를 켠 상태와
   끈 상태를 비교한다. 이것이 이 작업의 합격선이다.
3. 측정 1회 소요 시간을 로깅해 500ms 예산 대비 여유를 확인한다.
4. 렌즈를 가려 값이 0 근처로 가는지, 밝은 조명으로 포화율이 오르는지 확인한다.

2번이 실패하면 나머지가 모두 통과해도 목표를 달성하지 못한 것이다.
