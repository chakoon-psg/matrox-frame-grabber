# 판독기 적용 전후 실측 — 2026-09-14

학습 판독기(ONNX)를 앱에 실제로 붙이고, **같은 프로토콜로 전후를 재서** 영향을 기록한다.
`docs/adr/0002-screen-inspector-as-a-removable-slice.md`가 설계이고 이 문서가 그 결과다.

지금까지 판독기 비용은 **별도 프로세스**로만 쟀다. ADR의 "이 실측이 말하지 않는 것"에
그렇게 적혀 있다 — 인프로세스면 GC와 틱 스레드를 공유하므로 다를 수 있는데 확인한 적이 없고,
UI 응답성은 로그로 알 수 없다. 이 문서가 그 둘을 채운다.

## 프로토콜

양쪽 모두 동일하다. 하나라도 다르면 비교가 아무 말도 하지 못한다.

- 3채널 · decim 2 · 1024×772 · 노출 8289 µs → **120.0 fps**
- 일곱 종류 전부 켬, 증거 기록 켬
- **10분**(600초) 헤드리스 실행(`--autostart 600`)
- 실행 중 PC에서 **다른 일을 하지 않는다** — 빌드 하나가 유실을 만든다(두 번 확인)
- 재는 것 셋:
  - **유실 프레임** · **reduce 시간** — 앱이 종료 시 스스로 보고
  - **UI 스레드 지연** — 프로세스 밖에서 `SendMessageTimeout(WM_NULL)` 왕복.
    앱에 아무것도 추가하지 않고 재며, 로그로는 알 수 없는 유일한 값이다

스크립트는 `$CLAUDE_JOB_DIR/tmp/measure.ps1` 하나이고 태그만 받는다.

### 먼저: 두 실행의 장면이 같지 않았다

**사건이 0/0/0에서 12/5/5로, 쓸림 기각이 2/2/2에서 66/40/50으로 늘었다.** 이건 판독기와
무관하다 — 판독기는 `RecordAnomaly`를 부르지 않는다. **방에 사람이 있었다**는 신호다
(onset-spread 게이트가 걸러 낸 수가 20배인 것이 그 서명이고, 이 저장소가 이미 적어 둔
"이 방의 이상 대부분은 패널이 아니라 사람이다"의 모습이다).

**그래서 장면에 따라 변하는 값은 비교할 수 없다.** reduce 평균이 ch0에서 229 → 189 µs로
*내려간* 것이 그 예다 — 판독기를 붙였는데 축약이 빨라질 이유는 없고, 화면 내용이 달라진 것이다.

**비교할 수 있는 것은 셋뿐이다:** 유실 프레임, 판독기 자신의 비용, UI 지연의 중앙값·p90.

## 영향

### ① 유실 프레임: 0 → 0. 판독기는 프레임을 먹지 않는다

가장 중요한 결과이고, 별도 프로세스로 잰 값이 인프로세스에서도 유지된다는 확인이다.
GC와 틱 스레드를 공유해도 결과가 같다 — ADR이 "확인한 것은 아니다"라고 남겨 둔 항목이 닫혔다.

**여유가 얼마나 되는지도 나왔다.** 판독 1회가 약 5 ms이고 2초에 한 번이므로 **duty 0.25%**
(세 채널 합 0.75%)다. 실측 상한이 약 212회/초였으니 지금 쓰는 것은 그 용량의 **0.7%**다.
필요하면 순찰을 훨씬 촘촘하게 돌려도 된다.

### ② 인프로세스 비용은 추론만의 값보다 약 0.7 ms 크다

| | 값 | 무엇을 포함하나 |
|---|---|---|
| 별도 프로세스, 추론만 (2026-09-11) | 4.602~4.711 ms | 추론 |
| **인프로세스, 끝에서 끝까지 (오늘)** | **4.675~5.017 ms** | ROI 읽기 + 레터박스 + 추론 + 디코드 |

**즉 ROI 읽기 + 레터박스 + 디코드를 다 합쳐 약 0.3~0.4 ms다.** cs 문서 §8이 "전처리+디코드는
추론의 2% 미만"이라고 한 것과 자릿수가 맞는다(우리는 ROI 읽기가 더 들어가 있어 조금 크다).

판독 1회 최대는 8.0~15.2 ms로 평균의 2~3배까지 튄다. 프레임 주기 8,333 µs를 넘는 값이지만
**취득 예산 안에서 도는 일이 아니라** 유실로 이어지지 않는다.

### ③ UI 응답성: 평상시 영향 없음, 꼬리는 나빠졌다 (표본 하나)

| | 적용 전 | 적용 후 |
|---|---|---|
| 중앙값 | 0.10 ms | **0.10 ms** |
| p90 | 0.16 ms | **0.17 ms** |
| p99 | 7.16 ms | 8.18 ms |
| 최대 | 19.25 ms | **69.51 ms** |

**중앙값과 p90이 그대로다** — 평상시 UI는 판독기를 느끼지 못한다. ADR이 "로그로는 알 수 없다"고
비워 둔 항목의 답이다.

**최대값이 3.6배가 됐다.** 다만 **이건 표본 하나이고, 실행당 한 번 나오는 값이라 한 쌍의 실행으로
판독기 탓이라고 말할 수 없다.** p99가 7.16 → 8.18로 거의 안 움직인 것을 보면 분포 전체가 밀린
것은 아니다. 69.5 ms는 사람이 알아챌 수 있는 멈칫거림이므로 **반복 실행으로 확인할 값**이지
지금 결론 낼 값이 아니다.

### ④ 배포 크기: +16.0 MB — 그런데 고치지 않았으면 +245 MB였다

**ADR에 적었던 +27.6 MB는 실제와 달랐다.** 처음 빌드한 출력이 **459.7 MB**였고, 원인은
ONNX 패키지가 **자기가 지원하는 모든 플랫폼의 네이티브 라이브러리를 출력에 복사**하는 것이었다.

| runtimes/ 내역 | 크기 |
|---|---|
| ios | 56.9 MB |
| android | 49.5 MB |
| osx-arm64 | 41.2 MB |
| linux-x64 | 27.2 MB |
| linux-arm64 | 23.6 MB |
| win-arm64 | 15.5 MB |
| **win-x64 (쓰는 것)** | **15.4 MB** |
| 합계 | 229.3 MB |

**이 WPF x64 앱이 절대 돌 수 없는 운영체제용 214 MB가 현장에 나갈 뻔했다.**
`RuntimeIdentifier`를 `win-x64`로 고정해 해결했다(`AppendRuntimeIdentifierToOutputPath`를
false로 두어 출력 경로는 문서에 적힌 그대로 유지).

고친 뒤 실측:

| | 총 크기 | ffmpeg | 앱 부분 |
|---|---|---|---|
| 적용 전 | 214.4 MB | 212.0 | **2.4 MB** |
| **적용 후** | **230.4 MB** | 212.0 | **18.4 MB** |
| 차이 | **+16.0 MB** | — | +16.0 |

여기에 모델 파일 **8.8 MB**가 더해진다(빌드 산출물이 아니라 런타임 탐색 대상이라 ffmpeg와 같은
취급이다). **합계 +24.8 MB.**

**비율로 읽으면 두 이야기가 다르다.** 전체 대비로는 +7%지만, ffmpeg를 뺀 **앱 자체는
2.4 MB에서 18.4 MB로 7.7배**가 된다. 어느 쪽이 맞는 관점인지는 배포를 어떻게 하느냐에 달렸다.

### ⑤ 제거 비용: 세 가지, 실제로 빼서 확인했다

문서상 주장이 아니라 **정말 지워 보고 빌드하고 돌렸다.**

1. `src/MatroxFrameGrabber.csproj`의 `PackageReference` 한 줄
2. `src/Onnx/` 폴더
3. `src/App.xaml.cs`의 등록 람다

**결과: 빌드 경고 0 · 오류 0, 앱 정상 실행, 유실 0**, 그리고 로그가 설계대로 이유를 말한다:

```
Camera 0: inspector - no inspector implementation was registered in this build
```

호출 지점은 그대로 컴파일되고, 팩토리가 `NullScreenInspector`를 돌려주며, ORT 파일이 출력에서
사라진다. **`MilSeqVideoSink`가 한 번도 실행된 적 없는 골격으로 비용 0인 것과 같은 구조**이고,
이번에는 추정이 아니라 해 본 결과다.

### ⑥ 설계에서 달라진 것 셋

| 설계 | 실제 | 왜 |
|---|---|---|
| `src/Onnx/`를 **별도 어셈블리**로 | **앱에 컴파일** | 계약이 Infrastructure에 있고 그건 앱 exe에 들어간다. 별도 프로젝트는 소스 포함으로만 접근 가능하고, 그러면 **같은 이름의 인터페이스가 둘**이 되어 아무것도 올바른 쪽을 구현하지 못한다. Infrastructure를 라이브러리로 빼면 되지만 테스트 구성까지 바뀐다 |
| 출력 채널 `[heat, offY, offX, h, w]` | **`[heat, h, w, offY, offX]`** | 하니스가 격자 전체 범위를 찍어 확인했다. 채널 0은 전부 음수(= 아무것도 못 찾은 히트맵), 나머지는 범위로 갈린다. **쌍 안의 순서는 여전히 미확인** |
| 판독기가 **전체 프레임**을 본다 | **분석 ROI**를 본다 | ROI가 284×176~306×200이라 모델 입력(320×256)보다 **작다**. 즉 축소가 아니라 **확대**이고, 레터박스의 box average 경로는 실제로 안 쓰인다. ADR의 1024×772 산술은 이 리그에 해당하지 않는다 |

### ⑦ 여전히 못 한 것

- **정확도 미측정.** 이 모델은 "green" 단일 클래스라 AVN 화면에서 아무것도 찾지 않는다
  (10분 동안 findings 0건). 판정 품질은 우리 문제를 배운 모델이 있어야 잴 수 있다.
- **쌍 안의 채널 순서 미확인.** 좌표가 어디에 그려지는지가 달라지지만, 비용에는 영향이 없다.
- **UI 최대값의 원인 미확정**(③).
- **타일 검출기와 판독기가 다르게 말할 때의 규칙 없음.** 그래서 지금 findings는 로그로만 가고
  `RecordAnomaly`를 부르지 않는다.

## 결론

**비용 면에서는 붙여도 된다는 것이 확인됐다.** 3채널 120 fps 옆에서 인프로세스로 돌려도
유실 0이고, 용량의 0.7%만 쓰고 있으며, 평상시 UI 응답성은 변하지 않는다. 제거도 세 줄이고
실제로 해 봤다.

**그래도 지금 켜 두지 않는다.** 답할 모델이 없어서다 — 10분 동안 findings 0건이 그 사실을
그대로 보여 준다. 기본값은 꺼짐이고, `docs/adr/0002`의 권고(하니스 먼저, 통합은 모델이 생긴
뒤에)는 그대로다.

**이 실행이 바꾼 것은 셋이다:** 인프로세스 비용과 UI 영향이 추정에서 실측이 됐고,
배포 크기가 +27.6 MB 추정에서 **+245 MB의 함정과 +24.8 MB의 실측**으로 바뀌었으며,
제거 비용이 주장에서 **해 본 결과**가 됐다.
