# 로케이터 처리 속도 실측 — 초당 몇 번 볼 수 있나 (2026-09-16)

판독기를 **ROI 로케이터**로 쓸 때(전체 프레임 입력) 초당 몇 프레임을 처리할 수 있는지,
그리고 그것이 **고속 검출(타일 7종)의 프레임레이트를 깎는지**를 잰다.

설계 검토는 [`../2026-09-16-inspector-roi-vs-full-frame.md`](../2026-09-16-inspector-roi-vs-full-frame.md).

---

## 한 줄

**취득 옆에서 초당 118회.** 그리고 **고속 검출은 184.1 fps 그대로다** — 대조군이 오히려 더 많이
잃었다.

---

## 무엇을 쟀나

**앱의 코드를 그대로 잰다.** 벤치가 `BgrLetterbox`와 `OnnxScreenInspector`를 **소스로 포함**해서,
`CameraChannel.Inspect`가 하는 일과 같은 순서로 돈다 — 공유 평면 프레임에서 레터박스를 채우고,
그래프를 돌리고, 디코드한다. `tools/OnnxInspector`가 소스 포함을 하는 이유와 같다.

| | |
|---|---|
| 모델 | `green_detector_192_fp32.onnx` (8.8 MB), 입력 **320×256**, 격자 **80×64 (stride 4)** |
| 세션 | ORT 기본 스레드, `allow_spinning=0` (앱과 같은 설정) |
| 반복 | 각 기하 200회 (워밍업 20) |
| 프레임 | 합성 — 어두운 배경에 밝은 사각형. 그래프의 시간은 텐서 내용에 의존하지 않는다 |
| 머신 | 이 PC. 다른 작업 없음 |

**격자가 stride 4로 확인됐다.** 앞선 문서들이 `[추정]`으로 달아 둔 값이고, 이제 모델 메타데이터로
확인된 값이다(`grid 80x64`).

세 가지 기하:

| | 소스 | 레터박스 | 무엇인가 |
|---|---|---|---|
| **A** | 284×176 (1024×772 안의 ROI) | ×1.127 **확대** → 320×198 | **현재 배선** |
| **B** | 1024×772 전체 | ×0.3125 축소 → 320×241 | **로케이터 (decim 2)** |
| **C** | 2048×1544 전체 | ×0.15625 축소 → 320×241 | 로케이터 (decim 1) |

## ① 유휴 상태 (12:5x, 취득 없음)

| | 레터박스 median | 추론+디코드 median | **합계 median** | **초당** |
|---|---|---|---|---|
| A ROI 크롭 | 0.230 ms | 2.897 ms | 3.126 ms | **320회/초** |
| **B 전체 프레임 (decim 2)** | **0.666 ms** | 2.796 ms | **3.439 ms** | **291회/초** |
| C 전체 프레임 (decim 1) | 2.121 ms | 2.894 ms | 5.028 ms | 199회/초 |

추론 2.80~2.90 ms는 이 저장소가 이미 잰 유휴 값(2.696 ms)과 cs 문서의 2.77 ms와 같은 자리다.

## ② 취득 옆 — **3채널 · 184.1 fps · decim 2 · 일곱 종류 켬** (12:55:58)

이 저장소의 규율대로 **돌고 있는 그랩 옆에서** 다시 잰다. 이쪽이 판단에 쓸 값이다.

| | 레터박스 median | 추론+디코드 median | **합계 median** | p90 | max | **초당** |
|---|---|---|---|---|---|---|
| A ROI 크롭 | 0.395 ms | 6.690 ms | 7.100 ms | 8.39 | 12.55 | **141회/초** |
| **B 전체 프레임 (decim 2)** | **1.535 ms** | 6.882 ms | **8.463 ms** | **10.04** | **12.95** | **118회/초** |
| C 전체 프레임 (decim 1) | 5.146 ms | 6.604 ms | 11.778 ms | 13.10 | 15.12 | 85회/초 |

**취득 옆이면 2.4배 느려진다**(B: 3.44 → 8.46 ms). 추론이 2.80 → 6.88 ms로 2.5배인 것이 대부분이고,
이건 09-11에 별도 프로세스로 잰 "취득 옆 4.60~4.71 ms"보다도 크다 — **그때는 120 fps였고 지금은
184.1 fps다.** 즉 이 표는 문서화된 운전점(120 fps)보다 **불리한 조건에서 잰 값**이다.

## ③ 고속 검출은 깎이지 않는다 — 대조군까지 두고 확인

같은 설정으로 180초씩 두 번 돌렸다. 하나는 벤치를 옆에서 돌리면서, 하나는 아무것도 없이.

| | ch0 | ch1 | ch2 | 실효 레이트 |
|---|---|---|---|---|
| **벤치를 돌리며** (12:55:18~12:58:20) | 33,395 프레임 / **145 missed** | 33,076 / **365** | 33,198 / **144** | 183.8~184.1 fps |
| **대조군, 벤치 없음** (12:58:37~13:01:42) | 33,375 / **254** | 33,277 / **458** | 33,431 / **237** | 184.1~184.2 fps |

**대조군이 더 많이 잃었다.** 즉 이 유실은 로케이터 부하가 아니라 리그 자신의 활동이다 —
두 실행 모두 시작 직후 Blackout 사건이 나면서 증거 덤프를 썼고(226 MB, 204 MB), ch1은 내내
Dropout 쓸림을 기각하고 있었다. 그리고 **184.1 fps는 이 저장소가 정한 운전점(120 fps)이
아니다** — 3채널 합 1.31 GB/s다.

**말할 수 있는 것:** 초당 118회를 **쉼 없이** 돌리는 최악 부하에서도 취득 프레임레이트가 변하지
않았고 유실이 늘지 않았다. 실제 상시 운전은 이것의 **3% 이하**를 쓴다(아래).

## ④ 그래서 상시 운전의 실제 부하

로케이터는 매 프레임이 아니라 틱에서 돈다. 운전 후보별로:

| 주기 | 3채널 합 | 1초에 쓰는 시간 (8.46 ms 기준) | **duty** | 용량 대비 |
|---|---|---|---|---|
| **틱마다 한 채널씩 (라운드로빈, 채널당 1.5초)** | 2.0회/초 | 16.9 ms | **1.7%** | 118회/초의 **1.7%** |
| 매 틱, 세 채널 모두 (채널당 0.5초) | 6.0회/초 | 50.8 ms | **5.1%** | **5.1%** |
| 2초에 1회 (현재 판독기 주기) | 1.5회/초 | 12.7 ms | 1.3% | 1.3% |

**장비 이동은 초 단위로 일어나는 일이 아니므로 라운드로빈으로 충분하고, 그것이 1.7%다.**

## ⑤ 검토 문서의 추정 둘을 고친다

| | 추정이었던 값 | **실측** | 무엇을 놓쳤나 |
|---|---|---|---|
| 전체 프레임 레터박스 비용 | 읽는 픽셀이 12.5배니 **시간도 그만큼** | **2.9배** (0.230 → 0.666 ms 유휴 / 0.395 → 1.535 ms 취득 옆) | ROI 경로는 **확대**라 목적지 픽셀마다 소스 한 점만 읽는다 — 읽는 양은 적어도 루프 오버헤드는 같다. 전체 프레임 쪽은 박스 평균이 **순차 접근**이라 바이트당 비용이 훨씬 싸다 |
| 판독 1회 합계 | **[추정]** 6.6~8.1 ms | **8.46 ms** (median, 취득 옆) | 추정이 맞는 자리에 떨어졌지만, 그건 120 fps 가정이었고 실제 측정은 184 fps 옆이다 |

**그리고 stride 4 가정이 확인됐다** — `grid 80x64`. 즉 전체 프레임을 넣었을 때 패널이 차지하는
격자 칸이 **22×14**라는 계산도 확인된 값이 됐다.

## 재현 방법

**`tools/OnnxInspector`의 `locator` verb다.** 처음엔 스크래치패드에서 쟀고, 그 하네스가 존재하는
이유가 *"숫자를 아무나 재현할 수 있게"*이므로 저장소로 옮겼다.

```
OnnxInspector locator <model.onnx> [--threads N] [--iterations N] [--warmup N]
                                   [--frame WxH] [--region WxH]
```

기하를 주지 않으면 앱이 실제로 넘길 수 있는 셋(A·B·C)을 차례로 돈다. 주면 그 하나만 돈다 —
채널마다 ROI가 다르므로(`284x176` / `306x200` / `274x186`) 그 채널의 값을 보고 싶을 때 쓴다.

`bench`와 다른 점: `bench`는 이미 모양이 맞은 텐서를 그래프에 먹여 **그래프**를 재고,
`locator`는 **레터박스 → 그래프 → 디코드** 전체를 잰다. 순찰 주기를 정하는 것은 후자다.

`BgrLetterbox` · `CenterNetDecoder` · `OnnxScreenInspector`를 **소스로 포함**하므로
여기서 나온 숫자는 앱에 대한 숫자다(`csproj`의 `Compile Include` 참고).

**하네스로 옮긴 뒤 유휴 재현값**(스크래치패드 값과 실행 간 산포 안에서 일치):

| | 스크래치패드 | 하네스 |
|---|---|---|
| A ROI 크롭 | 3.126 ms | 3.020 ms |
| B 전체 프레임 (decim 2) | 3.439 ms | 3.307 ms |
| C 전체 프레임 (decim 1) | 5.028 ms | 5.075 ms |

---

## 이 측정이 말하지 않는 것

- **인앱 값이 아니다.** 로케이터가 아직 앱에 없으므로 별도 프로세스로 쟀다. 09-14 실측에서
  인프로세스는 별도 프로세스보다 약 0.3 ms 컸다(GC·틱 스레드 공유). 같은 폭이라면 8.46 → 약 8.8 ms다.
- **틱에서의 MIL 읽기(2.37 MB)가 빠져 있다.** 벤치는 이미 호스트 메모리에 있는 배열을 읽는다.
  실제 로케이터는 디스플레이 버퍼에서 밴드 셋을 `MbufGet2d`해야 하고, 그 비용은 아직 안 쟀다.
- **정확도는 재지 않았다.** findings 0건은 이 모델이 "green" 단일 클래스이기 때문이고, 합성
  프레임에서도 같다. **처리 속도만의 측정이다.**
- **운전점이 아니다.** 184.1 fps에서 쟀다. 문서화된 운전점 120 fps에서는 추론이 덜 느려질
  것이므로 이 표는 보수적인 쪽이다.
- 두 실행 모두 유실이 0이 아니었다. 원인은 리그의 사건 활동과 184 fps이고, 대조군 비교로
  **로케이터 부하가 아님**만 확인했다.
