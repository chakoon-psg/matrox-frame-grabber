## 실측이 가르친 것 (다음 사람이 알아야 할 것)

**바닥의 방향이 종류마다 반대다.** 이걸 모르면 실행 길이를 잘못 고른다.

| 종류 | 재는 것 | 실행이 길어지면 | 짧은 실행은 |
|---|---|---|---|
| Dropout | 잡음의 **최대** depth | 바닥이 **올라간다** | 임계값을 너무 낮게 잡는다 |
| Blackout | 작동 패널의 **최소** luma | 바닥이 **내려간다** | 임계값을 너무 높게 잡는다 |
| Washout | 작동 패널의 **최대** luma | 천장이 **올라간다** | 임계값을 너무 낮게 잡는다 |
| Freeze | 살아있는 변화의 **최소** | 바닥이 **내려간다** | 임계값을 너무 높게 잡는다 |

**네 경우 모두 짧은 실행이 낙관적이다.** 방향만 다를 뿐이다.

**테스트에 개수를 굳히지 말 것.** "Dropout만 구현됨" → "두 종류" → "세 종류"로 세 번 깨졌고,
깨진 날은 매번 **검출기를 추가한 날**이었다 — 테스트가 조용해야 할 유일한 날이다. 지금은 속성으로
바꿨다: `Implemented`와 `EnabledCount`가 어긋나지 않을 것, 구현된 종류는 지속형이거나 사건형일 것.

**`KindSettings`에 필드를 더하면 `CopyFrom`·`Clamp`·`Resolve` 셋 다 고칠 것.** Blackout에서
다섯 개를 빠뜨려 값이 조용히 버려졌다. Washout·Freeze는 처음부터 셋 다 넣었다.
